# Integrity and Reliability Reflection

Replication is what saved my data when node2 failed. Every block had 2 copies on different nodes, so when node2 went down I didn't actually lose any loans. The January and February blocks were still on node1 and node3, so I just copied them to a new node and everything was back to 2 copies. That's basically what fault tolerance is, the system expects things to break so it keeps extra copies. One thing I noticed is that right after node2 failed, those 2 blocks only had 1 copy left, so if another node went down at that point the data would be gone. I think that's why a lot of real systems use a replication factor of 3 instead of 2.

Partitioning helps in a different way. Since my lake has a folder for each year and month, DuckDB can skip the folders it doesn't need. For my 2025 campus query it didn't have to read the 2024 folder at all. With only 30 rows it doesn't really matter, but with years of loan data it would save a lot of time. It also makes it less likely to accidentally pull in old data, since the dates are part of the folder setup and not just something you have to remember to filter for.

If this was a real data lake it would need a lot more than just folders and copies. There should be checks when new data comes in, like making sure the dates are in the right format, there are no duplicate loan IDs, and the campus and item names are spelled the same every time. There should also be a way to check that the copies on each node actually match and didn't get messed up. It would need access controls so only the right people can see or change the loan data, and some kind of catalog so people know what each dataset is and who's in charge of it. Without that, the data lake could turn into a mess where nobody trusts the data.
